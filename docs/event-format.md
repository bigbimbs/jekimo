# Event format

This document is the public contract for the Jekimo event envelope, **schema version 1**. How envelopes are sent over HTTP is specified in [ingestion-protocol.md](ingestion-protocol.md). Every SDK produces it, the ingestion API accepts it, the worker and storage keep it, and exports return it. The reference implementation is `packages/event-schema`: TypeScript types, a validator, a JSON Schema at `schema/event-envelope.v1.json`, and the example payloads in `examples/`.

Key words **MUST**, **MUST NOT**, **SHOULD**, and **MAY** are used as in RFC 2119.

Status: draft. The contract may change until the first stable release. After that, changes follow the compatibility rules at the end of this document.

## Design goals

- One envelope for every event source, so browser and mobile SDKs can be added later without changing the pipeline.
- Safe by default: nothing sensitive is collected unless the operator opts in, and configured secrets are redacted before transmission.
- Bounded: every field has a limit, so one noisy client cannot exhaust a VPS.
- Server-side project scoping: the client never chooses the project.

## Envelope

```json
{
  "schema_version": 1,
  "event_id": "01JBQ4Z3H8X9T2K7M5N6P8R9SV",
  "project_id": "prj_billing",
  "timestamp": "2026-11-05T09:14:33.412Z",
  "kind": "exception",
  "severity": "error",
  "message": "Database request failed while charging invoice",
  "service": "billing-api",
  "environment": "production",
  "release": "1.4.2",
  "fingerprint": "DatabaseError:charge-invoice",
  "exception": {
    "type": "DatabaseError",
    "value": "connection terminated unexpectedly",
    "stacktrace": "DatabaseError: connection terminated unexpectedly\n    at chargeInvoice (/app/src/invoices/charge.ts:42:19)"
  },
  "sdk": { "name": "@jekimo/sdk-node", "version": "0.1.0" },
  "context": { "request_id": "req_7f3c2a1b", "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736" },
  "attributes": { "invoice_id": "inv_000123", "retry_count": 2 }
}
```

More examples: [`exception.json`](../packages/event-schema/examples/exception.json), [`log.json`](../packages/event-schema/examples/log.json), [`custom-event.json`](../packages/event-schema/examples/custom-event.json).

## Two forms of the same envelope

| Form | Where it appears | `project_id` |
| --- | --- | --- |
| **Ingest** | Request body sent by an SDK | MUST be absent. The server rejects the event if present. |
| **Stored** | Storage, query API responses, exports | MUST be present. Set by the server from the ingestion key. |

Everything else is identical. The validator takes `mode: "ingest"` or `mode: "stored"`.

## Fields

Character limits count UTF-16 code units as reported by JavaScript `string.length`. Byte limits count UTF-8 bytes of the serialized JSON.

### Required

| Field | Type | Rules |
| --- | --- | --- |
| `schema_version` | integer | MUST be `1`. |
| `event_id` | string | A [ULID](https://github.com/ulid/spec): 26 Crockford base32 characters, first character `0`–`7`. Generated by the client. Unique within a project; the server deduplicates on `(project_id, event_id)` and treats a repeat as already accepted. |
| `timestamp` | string | RFC 3339 date-time with optional fractional seconds. UTC with `Z` is RECOMMENDED. The server rejects timestamps more than **5 minutes** in the future. Timestamps older than the project's retention window are accepted and expired immediately. |
| `kind` | enum | `exception`, `log`, or `event`. |
| `severity` | enum | `debug`, `info`, `warning`, `error`, or `fatal`. |
| `message` | string | 1 to 4,096 characters. A human-readable summary. SDKs truncate longer text and append `…`. |

### Optional

| Field | Type | Rules |
| --- | --- | --- |
| `project_id` | string | 1 to 64 characters. See "Two forms" above. |
| `service` | string | 1 to 128 characters. Logical service or application name. |
| `environment` | string | 1 to 128 characters. For example `production`, `staging`. |
| `release` | string | 1 to 128 characters. Version, tag, or commit of the reporting application. |
| `fingerprint` | string | 1 to 256 characters. Stable grouping key. When absent, the worker derives one (see "Grouping"). |
| `exception` | object | REQUIRED when `kind` is `exception`; MAY be attached to other kinds. See below. |
| `sdk` | object | Identity of the reporting SDK: `name` (1 to 64 characters) and `version` (1 to 32 characters), both required when the object is present. |
| `context` | object | Correlation identifiers. String keys 1 to 64 characters, string values up to 1,024 characters, at most 32 entries. |
| `attributes` | object | Free-form structured data. See below. |

### `exception`

| Field | Type | Rules |
| --- | --- | --- |
| `type` | string | Required. 1 to 256 characters. The exception class or type name. |
| `value` | string | Up to 4,096 characters. The exception's own message, which may differ from the envelope `message`. |
| `stacktrace` | string | Up to 65,536 characters. Raw stack trace text as produced by the runtime. Structured frames and source map support are planned as an additive change. |

### `context`

Reserved keys with defined meaning. Other keys are allowed.

| Key | Meaning |
| --- | --- |
| `request_id` | Identifier of the inbound request being handled. |
| `trace_id`, `span_id` | W3C Trace Context identifiers, when available. |
| `host` | Hostname or container name of the reporting process. |
| `runtime` | Runtime name and version, for example `node/22.11.0`. |

Do not put user identifiers, email addresses, or IP addresses in `context` unless the operator has decided to collect them. If a user identifier is needed for debugging, hash it in the SDK.

### `attributes`

Any JSON value, with these limits:

- At most 64 keys per object, each 1 to 64 characters.
- String values up to 1,024 characters.
- Numbers must be finite. `NaN` and `Infinity` are rejected.
- Arrays up to 32 items.
- Nesting depth at most 4, where `attributes` itself is depth 1. `{"a": {"b": {"c": 1}}}` is depth 3.

Attribute keys are subject to redaction (see "Privacy defaults").

## Size limits

| Limit | Value |
| --- | --- |
| One event, serialized | 128 KiB |
| Events per ingestion request | 100 |
| One ingestion request, serialized | 1 MiB |

The SDK is responsible for staying within these limits by truncating `message`, `exception.value`, `exception.stacktrace`, and attribute strings, and by dropping attributes when the event is still too large. The server rejects anything over the limit rather than truncating, so the behavior is predictable.

## Privacy defaults

SDKs MUST behave as follows unless the operator configures otherwise:

- Do not capture request bodies, response bodies, request headers, cookies, environment variables, or local variables.
- Redact the value of any `context` or `attributes` key whose name, lower-cased and with `-`, `_`, and spaces removed, is in the default list: `authorization`, `proxyauthorization`, `cookie`, `setcookie`, `password`, `passwd`, `secret`, `token`, `accesstoken`, `refreshtoken`, `idtoken`, `apikey`, `accesskey`, `secretkey`, `privatekey`, `clientsecret`, `sessionid`, `creditcard`, `cardnumber`, `cvv`, `ssn`. The value is replaced with the string `[REDACTED]`. The list is exported as `DEFAULT_REDACTED_KEYS`.
- Allow operators to add keys and regular expressions to the redaction list, and to disable capture of `context` entirely.
- Redact in the application process, before the event is serialized for transmission. The server does not see the original value.

The server additionally applies project-level redaction rules configured by the operator, so a misconfigured SDK is not the last line of defense.

## Unknown fields and forward compatibility

The ingestion API **ignores and drops** top-level fields it does not know, and unknown fields inside `exception` and `sdk`. It does not reject the event. This lets a newer SDK talk to an older server. The reference validator reports each dropped field as a warning with code `unknown_field`.

SDKs MUST NOT rely on unknown fields being stored.

## Validation errors

The validator returns a list of issues. Each has a `path` (JSON Pointer-style, `""` for the whole event), a `code`, and a `message`. The ingestion API returns the same shape in its `400` response body so SDK authors can debug payloads.

| Code | Meaning |
| --- | --- |
| `required` | A required field is missing. |
| `forbidden` | A field that must not be present was sent, for example `project_id` on ingest. |
| `type` | Wrong JSON type. |
| `enum` | Value not in the allowed set, including a wrong `schema_version`. |
| `min_length`, `max_length` | String or key length out of range. |
| `pattern` | String does not match the required format, for example a malformed `event_id`. |
| `max_keys`, `max_items`, `max_depth` | Object, array, or nesting limit exceeded. |
| `invalid_number` | Non-finite number in `attributes`. |
| `invalid_timestamp`, `future_timestamp` | Timestamp cannot be parsed, or is too far in the future. |
| `max_size` | Serialized event exceeds 128 KiB. |
| `unknown_field` | Warning only. The field was dropped. |

## Grouping

When `fingerprint` is absent the worker derives one:

- For `kind: exception`: from `exception.type` and the in-app frames of `exception.stacktrace`, with line numbers removed so a release does not split an issue.
- For other kinds: from `message` with numbers, UUIDs, and hex strings replaced by placeholders.

Sending an explicit `fingerprint` overrides this. The derivation algorithm may improve over time; existing issues keep their stored fingerprint.

## Delivery semantics

The envelope describes an event at three points:

1. **Created** in the application by the SDK.
2. **Accepted** by the ingestion API, which has validated it and written it to the durable queue. The API's `202` response lists accepted `event_id`s and per-event rejections.
3. **Stored** by the worker, after redaction and fingerprinting.

An SDK that receives `202` for an event may drop its local copy. Retries after a network failure are safe because of `event_id` deduplication.

## Compatibility rules

- **Additive changes** (new optional fields, new reserved `context` keys, new issue codes) do not change `schema_version`. Older servers drop the new fields as described above.
- **Breaking changes** (removing or renaming a field, changing a type, tightening a limit, adding a required field, adding an enum value that old servers must not misinterpret) increment `schema_version`. The server supports the previous version for at least one minor release cycle after the new one ships, and the deprecation is announced in `CHANGELOG.md`.
- Limits may be **raised** without a version change. They are only **lowered** with a version change.
- Every change to this document, the JSON Schema, or the validator ships in the same pull request, with tests.

## Open questions

- Structured stack frames (`exception.frames`) and source map handling for browser SDKs.
- Exception chains (`cause`).
- Whether `severity` should accept numeric levels from common logging libraries, mapped by the SDK.
