## [Unreleased]

### Added

- Invitations and password resets without email (`docs/access-model.md`, "Invitations and recovery without email"). An instance admin creates an invitation (`POST /api/v1/invitations`) or a reset link for a user (`POST /api/v1/users/:user_id/password-reset`) and receives a single-use link once, to hand over. The invitee sets their password with `POST /api/v1/invitations/accept`; a reset goes through `POST /api/v1/auth/password-reset` and signs the user out everywhere. Links expire after `JEKIMO_INVITE_EXPIRY_DAYS` (default 7), only their SHA-256 is stored, and the token travels in the URL fragment. Set `JEKIMO_PUBLIC_URL` to get full links instead of paths; the production Compose file defaults it to `https://$JEKIMO_DOMAIN` and passes the new API and worker settings. Emailing links over SMTP is not implemented.
- `jekimo admin reset-password <email>` prints a reset link on the server, for an instance admin who lost their password. It is on the `PATH` in the API image (`docker compose exec api jekimo admin reset-password <email>`).
- Account and session management: `POST /api/v1/auth/password` changes the password and revokes the user's other sessions; `GET /api/v1/auth/sessions` and `DELETE /api/v1/auth/sessions/:session_id` list and revoke the user's own sessions; instance admins revoke anyone's with `DELETE /api/v1/users/:user_id/sessions`.
- Instance user administration: `GET /api/v1/users` and `PATCH /api/v1/users/:user_id` change a user's instance role or deactivate and reactivate them. Deactivating ends their sessions. The last active instance admin cannot be demoted or deactivated (`409 last_admin`).
- Project memberships: `GET`, `POST /api/v1/projects/:id/members`, and `PATCH` and `DELETE /api/v1/projects/:id/members/:user_id` list, add (by email or user id), change, and remove members; `GET /api/v1/projects/:id/roles` lists roles with their permissions and member counts. A member manager can only grant, change, or remove roles whose permissions they hold (`403 role_escalation`). A project keeps at least one built-in admin (`409 last_admin`) unless an instance admin passes `force=true`.
- `PATCH /api/v1/projects/:id` changes a project's name, retention, and sample rate, with `settings.manage`.
- Ingestion key management: `GET /api/v1/projects/:id/keys` lists keys by `key_id` with name, creation time, and status, never the key or its hash; `POST .../keys/:key_id/rotate` returns a new key once and keeps the old one working for a grace period (`grace_hours`, default `JEKIMO_KEY_ROTATION_GRACE_HOURS` = 24); `POST .../keys/:key_id/revoke` revokes a key, and the next ingest request with it gets the same `401` as an unknown key.
- Audit log: every sensitive action is recorded with actor, action, target, time, source IP, and whether instance-admin authority was used, never with passwords, keys, session tokens, or event payloads. The actions are a typed list (`AUDIT_ACTIONS` in `@jekimo/storage-postgres`). Instance admins read it with `GET /api/v1/audit-log`, filtered by actor, action, and time, with paging. The worker's expiry pass deletes entries older than `JEKIMO_AUDIT_LOG_DAYS` (default 365); entries about deleted projects are kept until then.
- Database migration `0007`: an `account_tokens` table for invitation and reset links, and indexes for listing the audit log.

- Issues API: `GET /api/v1/projects/:id/issues` lists a project's issues, newest last seen first, filtered by status, kind, severity, environment, and time, with cursor pagination; `GET /api/v1/projects/:id/issues/:issue_id` returns one issue with its latest event; `POST .../resolve`, `.../ignore`, and `.../reopen` change its status. Reading needs `project.read`, changing status needs `issues.manage`, and users outside the project get `404`. Every status change is audit-logged with the status before and after. See `apps/api/README.md`.
- A resolved issue that receives a new event is reopened by the worker and the regression is audit-logged. Ignored issues stay ignored.
- `npm run recompute-issues -w @jekimo/worker` (or `node dist/recompute.mjs` in the worker image) rebuilds issue counts from the event store for every project or one project.
- Database migration `0009`: issues gain a stable `id`, the latest event id, the environments seen, and when and by whom their status last changed.
- `packages/event-schema` exports `deriveFingerprint`, the shared grouping derivation from `docs/event-format.md`, "Grouping": an explicit `fingerprint` is kept; exceptions group by type plus stack frames with line and column numbers removed, ignoring `node_modules` and `node:` frames unless no other frame is left; other kinds group by message with numbers, UUIDs, and hex strings replaced. The result is a 64-character SHA-256 hex digest. The worker now uses it. Exceptions whose frames are all library frames now group by those frames rather than by their message, so such issues may start a new group once after upgrading.
- `packages/event-schema` exports `redactEvent` and `createKeyRedactor`, one implementation of the default redaction from `docs/event-format.md`, "Privacy defaults", with extra keys, regular expression patterns, and an option to drop `context`. The Node SDK and the worker both use it; behavior is unchanged.
- `JEKIMO_MIGRATE_ON_START=true` makes the API and the worker apply pending migrations and create the coming week's event partitions before they start serving. It is off by default; `npm run migrate` and the dev stack's `migrate` service work as before. The worker image now carries the migrations too.
- Database migrations `0004` and `0005`: a project daily counters table (accepted, rejected, dropped, and sampled events per project per UTC day, kept 13 months per `docs/retention.md`) with idempotent increments, and a `redaction_rules` column on projects for operator-configured redaction keys and patterns. The worker and the ingest endpoint now fill the counters and the worker applies the rules; there is no API endpoint yet to read the counters or to set the rules.
- The worker validates every event in stored form (`validateEvent(..., { mode: "stored" })`) before storing it. An event that fails is not stored, is counted as dropped, and is logged with its index, `event_id`, and the failing paths and codes, never its content. Future timestamps are checked against the client's `sent_at`, as at ingest.
- The worker applies each project's redaction rules (extra keys, normalized like the default list, and regular expressions matched case-sensitively against the raw key name) on top of the default key list before storage. Rules are read once per project per batch, so a change applies from the next batch. If a stored pattern does not compile, the job fails and is retried rather than stored unredacted.
- Project daily counters are filled. After storing a job's events and updating its issues, the worker adds the job's accepted, dropped (failed stored validation), and sampled-out events to the UTC day of `received_at`, once per queue job even when the job is redelivered. Accepted counts every acknowledged delivery, including repeats of events stored earlier. `POST /api/v1/ingest` adds per-event rejections to the day's `rejected` counter; if that update fails the request still returns `202` and a warning is logged. The expiry pass deletes counters older than 13 months.
- `npm run bench -w @jekimo/worker` measures worker throughput against a throwaway schema in `JEKIMO_DATABASE_URL` (see `apps/worker/README.md`).
- `PostgresQueue.stats()` reports queue depth, the age of the oldest waiting job, and the number of dead-lettered jobs, for health checks.
- `packages/storage-postgres/README.md` lists the database privileges the runtime account needs.
- Event search: `GET /api/v1/projects/:id/events` now also filters by `kind`, `environment`, `release`, `fingerprint`, and `q` (words that must all appear in the message, served by a new full-text index on `message`). `GET /api/v1/projects/:id/events/:event_id` returns one event, needs a session and `project.read`, and answers `404` for an unknown id or one from another project. The event store gains `getEvent` and a `capabilities.textSearch` flag for engines where text search is expensive.
- Code tooling baseline: [Biome](https://biomejs.dev/) as the single linter and formatter (`biome.json`, `npm run lint`, `npm run lint:fix`, `npm run format`), with the repository formatted and `packages/event-schema` lint-clean. TypeScript now uses a shared `tsconfig.base.json` (adding `exactOptionalPropertyTypes` and `noUncheckedIndexedAccess`), a per-package `tsconfig.json`, and a solution-style root `tsconfig.json` checked with `tsc -b`. `npm run check` runs lint, type check, and tests, and CI runs them as separate steps. VS Code recommends the Biome extension.
- Node.js SDK `@jekimo/sdk-node` 0.1.0-alpha.0 in `packages/sdk-node`, implementing `docs/event-format.md` and the SDK requirements of `docs/ingestion-protocol.md`: `init`, `captureException`, `captureMessage`, `log`, `captureEvent`, `flush`, `close`, and `captureUnhandled`; monotonic ULIDs; `cause` chains in stack traces; truncation and size enforcement at every event limit; redaction of the default keys plus operator keys and patterns before serialisation; local sampling with `shouldKeepEvent`; a bounded queue that drops the oldest; batching at 100 events, 512 KiB, or 2 seconds; gzip above 8 KiB; retries with full-jitter backoff and `Retry-After`; 202 rejection reporting; and a bounded flush on process exit. Ships ESM, CommonJS, and type declarations with no runtime dependencies.
- Release machinery: a `release.yml` workflow that creates a GitHub Release from a `v*` tag with notes taken from this changelog and the event envelope JSON Schema and a `docs/` tarball attached; an `images.yml` workflow that builds multi-arch `ghcr.io/bigbimbs/jekimo-api` and `ghcr.io/bigbimbs/jekimo-worker` images (`edge` from `main`, versioned from tags) once the apps have Dockerfiles; and a `publish-sdk.yml` workflow that publishes `@jekimo/sdk-node` to npm with provenance from `sdk-node-v*` tags. The versioning policy, release checklist, and one-time setup are in `docs/releasing.md`.
- First draft of the VPS install guide in `docs/install-vps.md`: sizing and the storage formula, DNS and HTTPS with Caddy, existing or local PostgreSQL, environment variables, first-run setup, verifying ingestion, backups, upgrades and rollback, and troubleshooting. Steps that depend on unreleased code are marked as such.
- `docs/README.md`, an index of the documentation.
- First vertical slice from instance setup to a stored, queryable event. See `docs/local-development.md`.
  - `packages/storage-postgres`: `pg` connection module reading `JEKIMO_DATABASE_URL`, a plain-SQL migration runner (`npm run migrate`), metadata tables, an `events` table partitioned by UTC day of `received_at` with a 7-day `event_ids` deduplication index, and a `queue_jobs` table. Exposes `PostgresMetadataRepository`, `PostgresEventStore` (`appendEvents`, `queryEvents`, `expireDay`, and an `archiveDay` stub for Phase 2), and `PostgresQueue` (`FOR UPDATE SKIP LOCKED`, visibility timeout, bounded retries with backoff, dead-letter state). Project data is only reachable through a `ProjectAccess` issued after a membership check.
  - `apps/api` (Fastify): `GET /healthz` for liveness (the process is up, no database round trip) and `GET /readyz` for readiness (the database and the queue answer within 2 seconds, otherwise `503` with a `not_ready` error naming what is unreachable), which the API container's health check now calls; one-time setup with a console token that creates the first instance admin (Argon2id), the first project, and its ingestion key, returned once and never logged, after which `GET` and `POST /api/v1/setup` answer `404` and the token stops working; `JEKIMO_LOG_LEVEL` validated at start-up, so an unknown level stops the API with `invalid configuration: JEKIMO_LOG_LEVEL must be one of ...`; session sign-in and sign-out with `HttpOnly`, `Secure`, `SameSite=Lax` cookies, idle and absolute expiry, lockout, and a CSRF header; `POST` and `GET /api/v1/projects`; `POST /api/v1/projects/:id/keys`, which returns a `jk_` key once, stores only its SHA-256, and audit-logs the `key_id`; `POST /api/v1/ingest` per ingestion protocol v1 with constant-time key checks, content-type, gzip, and 1 MiB limits; and `GET /api/v1/projects/:id/events` by time range and severity. Ingestion keys are rejected on every other route and sessions cannot reach ingest. Rate limits are not implemented yet.

### Changed

- Every dashboard route, including setup, sign-in, and the invitation and reset routes, now rejects requests with an `Authorization` header with `401`, so an ingestion key reaches nothing but ingest.
- The database connection setting is now `JEKIMO_DATABASE_URL`. `DATABASE_URL` is still read when `JEKIMO_DATABASE_URL` is unset, logs a deprecation warning, and will be removed in a later release: rename it in your `.env`. `.env.example`, the dev Compose file, and CI use the new name.
- `POST /api/v1/ingest` returns `503 unavailable` with `Retry-After: 30` when the ingest queue already holds `JEKIMO_QUEUE_MAX_DEPTH` pending and running jobs (default 10,000), instead of accepting events it cannot hold. SDKs retry as for any other `503`.
- Event expiry now detaches a past day's partition before dropping it whenever the expiring project is the only one with events that day, and otherwise deletes the project's events for the day in one transaction, so an interrupted expiry pass never leaves part of a day visible. A partition left detached by an interrupted pass is dropped on the next pass.
- `.env.example` now lists every setting from the "Planned configuration" tables of `docs/retention.md`, `docs/access-model.md`, and `docs/object-storage.md`, grouped by spec with a link and a one-line description, set to its documented default or left empty. Object storage settings are marked Phase 2, and the two object storage credentials are empty with a reminder never to commit a real value. The local development and current API, queue, and worker settings are kept in their own groups, so `cp .env.example .env` still starts the dev stack.
- The ingestion protocol now states where cross-request deduplication happens: a repeat of an accepted `event_id` is listed in `accepted` and may pass through the queue again, and the worker drops it when appending to the event store. The window is at least 7 days from the stored copy's `received_at`; a repeat arriving after its entry was pruned is stored as a new event. Behavior is unchanged; `docs/ingestion-protocol.md` and `docs/retention.md` now match it.
- `CONTRIBUTING.md` has a "Local development" section on starting the stack, running setup, and sending a test event, and no longer describes the project as a scaffold. The curl walkthrough in `docs/local-development.md` builds its batch from `packages/event-schema/examples/` with `jq`.
- `SECURITY.md` now has a supported-versions table for `0.x` and states the policy from `1.0.0`: the latest minor, plus the previous minor for 90 days.
- Dependabot groups GitHub Actions updates into one pull request.
